【执行偏差与口径说明（均已按更严谨一侧实现，逐条给出证据）】

1. **REST 路径按真实引擎对齐（提示词 §8.4 与实测不符）**
   提示词写 `POST {SEATUNNEL_URL}/hazelcast/rest/maps/submit-job`。对 compose 固定的引擎镜像
   `flowpilot/seatunnel:2.3.13` 实测：该路径 **404**；真实契约是 SeaTunnel Zeta REST v2 的
   `/submit-job`（POST）、`/job-info/{jobId}`（GET）、`/stop-job`（POST）。
   证据（容器内实测）：`POST /submit-job → 500（进入 JobInfoService.submitJob，说明路径存在）`、
   `GET /job-info/1 → 200 {"jobId":"1"}`、`GET /running-jobs → 200 []`、
   `POST /hazelcast/rest/maps/submit-job → 404`。
   处置：客户端按**真实引擎**对齐（按提示词写路径只会得到稳定的 404），并在模块 docstring 记录口径；
   `test_rest_paths_match_real_engine` 断言路径常量。
   附带口径：状态字段名用 v2 的 `jobStatus`，并回落兼容旧版的 `status`；两者都缺失 → `UNKNOWN`
   （**不猜**成 RUNNING/FINISHED，猜错会把「不知道」写成终态）。

2. **引擎 `submit-job` 仍 500（引擎侧问题，非本阶段可闭环）**
   实测提交最小合法作业（FakeSource → Console）返回 `HTTP 500 {"status":"fail","message":null}`，
   引擎日志栈为 `ConfigShadeUtils.processConfig` NPE（`seatunnel-starter.jar:2.3.13`），
   与 jobName / jobId / 请求体形态无关（JSON 与 form 两种编码、含/不含 jobId、含/不含 `env.job.name` 均复现）。
   处置：本阶段 DoD-10 只要求「mock 可跑」（REST 提交 + CLI `--check` 由 MockTransport / 伪 CLI 覆盖）；
   真实引擎端到端提交列入 S8/e2e（AC-07 原子发布链路）前置项，见「遗留问题 1」。

3. **compose 补容器内寻址与 SeaTunnel 启动命令（人类文件的最小增量修改）**
   中断点前人类已写好 4 个服务，但实测起不来：

4. **API-11 的语义裁决：触发 = 点火，不是再授权**
   `Commit`（API-10）已签发令牌并同事务写入 `ExecutionRun(QUEUED)` + `Outbox(PENDING)`，
   故 API-11 不再授权，而是**把一次立即扫描派发到 Broker**（`worker.scan_outbox`），
   让已授权的命令不必等 Beat 的 2s 周期；**不在 API 进程内调引擎**（SPEC 3.2：Worker 才是执行通道）。
   派发失败不阻塞响应（返回 `dispatched=false`，Beat 周期兜底，FR-35）。
   出参 `dispatched` 字段把「是否已即时派发」变成可观测事实，而不是让调用方猜。

5. **令牌交接通道落在 Redis（S6 收尾留下的口径空白）**
   S6 的 Commit 只把令牌本体放进返回值一次，库中只存 `token_sha256`（FR-33），
   但**没有定义令牌怎么到达 Worker**——不解决就是「授权了但执行不了」。
   本阶段落地为 Redis 单次读通道（`GETDEL`，键 `harness:capability:{token_id}`，TTL 与 Capability 对齐），
   Commit 提交业务事务后写入；通道不可达 → 503 拒绝执行，**不降级为无令牌执行**（FR-34 红线）。
   不放 Outbox payload 的原因：payload 落业务库 JSON 列，令牌本体入库即违反「库中只存摘要」。

6. **`consume_outbox` 的推进节奏：跨遍推进而非单遍长轮询**
   提示词 §8.4 写「单遍扫描内轮询引擎（间隔 2s、最长 300s）」。实现为**每遍查一次引擎状态**：
   Beat 节奏 2s 天然构成轮询间隔；若在任务内长轮询，一个 2s 任务会被拖成分钟级，
   单副本 Beat 下直接阻塞后续周期。`execution_poll_max_wait_seconds` 改用作**停滞告警阈值**
   （超过即记一条 WARN 事件，不硬中断——硬中断属 S8 监督链路）。

7. **`SUBMITTED → CANCELLING` 补入状态机白名单（实现期发现的真实缺陷）**
   进入 SUBMITTED 即意味着引擎作业已提交（`seatunnel_job_id` 已写入），取消同样需要
   「申请 → 等引擎终止确认」两段式；原白名单只允许 `SUBMITTED → CANCELLED` 一步到位，
   会让运行在引擎侧仍在收尾时被标记为已终止。`test_cancel_from_submitted` 首轮即暴露。

8. **`request.state.trace_id` 被认证中间件覆盖（实现期发现的真实缺陷）**
   S2 的 `AuthMiddleware` 每次请求自行 `uuid4().hex` 写 `request.state.trace_id`，
   它位于可观测中间件内层 → 响应头的 trace_id 与错误体的 trace_id 不一致
   （日志里搜得到、响应对不上）。改为**沿用已有值，缺失才兜底生成**。

9. **占位符契约以 yaml 为唯一事实源（提示词 §8.3 的「10 个变量」与 `SRC_DATABASE` 为笔误）**
   `configs/credential_placeholders.yaml` 实际登记 11 项：`SRC_HOST/PORT/DB/USER/PASSWORD`、
   `SINK_HOST/PORT/DB/USER/PASSWORD`、`FILE_ASSET_BASE`。物化按契约**动态加载变量表**，
   契约增删不需改代码；`test_contract_registers_all_variables` 断言变量集一致。

10. **调度触发的授权口径：调度不自行授权，只创建受管准备单**

    （PDP 评级 + 四眼审批 + Commit 仍由 OPERATOR 走 API-10），`trigger=SCHEDULED` 的事实体现在
    `schedule_id` / `scheduled_for`。无状态到期判定：`pipeline_schedules` 无「上次触发」列
    （SPEC 5.2），以 `created_at` 为锚点反推最近已到期槽位；同一槽位因幂等键
    `sched-<schedule_id>-<槽位时刻>` 命中同一张准备单（FR-31 幂等语义），
    FIRE_ONCE 的「只补一次」由此天然成立，也不需要新增状态列（禁止事项 7）。
    环境 / 工具事实复用该版本最近一次准备单的登记值（调度不新造环境与工具版本）。
